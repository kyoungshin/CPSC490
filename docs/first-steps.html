Before you start

Your team repository already exists and is set up: every one of the 20 group repos has the course scaffold, the develop branch, the labels and the four sprint milestones. This guide starts from there. In the commands, replace OWNER/REPO with your repository, for example your-username/CPSC490-G00-Example, and replace 12 with your real issue number.

On Windows, type the commands in Git Bash (installed with Git). Where PowerShell needs something different, the guide shows both.

STEP 1

Set up your laptop

Everyone · once · about 20 minutes

Install three tools

Git tracks every change. GitHub CLI (gh) creates issues and pull requests from the terminal. Python runs the course checks and the story-point report.

Windows · PowerShell (run as yourself)
winget install --id Git.Git -e
winget install --id GitHub.cli -e
winget install --id Python.Python.3.12 -e
# close and reopen the terminal, then open "Git Bash" from the Start menu
macOS · Terminal
xcode-select --install          # gives you git
brew install gh python          # needs Homebrew: https://brew.sh

Check that all three answer with a version number:

Git Bash / Terminal
git --version
gh --version
python --version      # on Windows, if this fails try:  py --version

Tell git who you are

Use the same email as your GitHub account. If it differs, your commits do not count on the contributor graph, which is how individual work is seen.

Git Bash / Terminal
git config --global user.name "First Last"
git config --global user.email "you@csu.fullerton.edu"
git config --global init.defaultBranch main

Log in to GitHub from the terminal

Git Bash / Terminal
gh auth login
#   ? Where do you use GitHub?            GitHub.com
#   ? Preferred protocol for Git?         HTTPS
#   ? Authenticate Git with credentials?  Yes
#   ? How would you like to authenticate? Login with a web browser
gh auth refresh -s project     # lets gh work with your Sprint Board
gh auth status                 # should say "Logged in to github.com"

Download your team repository

Cloning copies the whole repository, with its history, into a folder on your laptop.

Git Bash / Terminal
cd ~/Documents                                   # or wherever you keep projects
git clone https://github.com/OWNER/REPO.git
cd REPO
git switch develop                               # your team's working branch
git pull                                         # get the latest
ls -a                                            # you should see .github  docs  proposal  prototype  scripts

If git switch develop fails

Your team leader has not run bash scripts/bootstrap.sh yet (QUICKSTART step 4). Ask them to run it, then try again.

STEP 2

The git loop you repeat for every change

Everyone · learn once, use all semester

Every change, whether a proposal paragraph or prototype code, follows the same eleven steps. Learn this once; Steps 3 to 8 just apply it.

WordWhat it means here
mainReleased work only: what you submitted or demoed. Nobody commits to it directly.
developThe team's shared working copy. Finished work lands here through pull requests.
branchYour private copy for one issue, e.g. feature/12-abstract. Always starts from develop.
commitA saved snapshot of your changes, with a message.
pushUpload your branch's commits to GitHub.
pull request (PR)A request to merge your branch into develop. A teammate reviews it; CI checks it.
  1. Know your issue number. Every change belongs to an issue (Step 5 shows how to file one). Say it is #12.
  2. Start from the latest develop.
  3. Make a branch named after the issue.
  4. Edit the files in VS Code or any editor.
  5. See what changed.
  6. Stage the files you meant to change, by name. Never stage everything blindly.
  7. Commit with a message that says what and names the issue.
  8. Run the course check (the harness). Fix anything red.
  9. Push your branch to GitHub.
  10. Open a pull request into develop. The template asks you to link the issue (Closes #12), say what you verified, and disclose AI use.
  11. A teammate who is not the author approves, CI is green, then squash-merge and go back to develop.
Git Bash / Terminal · the whole loop
# 2. start from the latest develop
git switch develop
git pull

# 3. one branch per issue: feature/<issue-number>-<short-name>
git switch -c feature/12-abstract

# 4. edit, for example:
code proposal/proposal.md          # opens VS Code; any editor works

# 5. see what changed
git status                         # which files changed
git diff                           # the exact lines (press q to quit)

# 6. stage the file(s) by name
git add proposal/proposal.md

# 7. commit
git commit -m "docs(proposal): draft §0 abstract (#12)"

# 8. the course check — must end green
python .github/scripts/check_repo.py

# 9. push (the -u is only needed the first time for this branch)
git push -u origin feature/12-abstract

# 10. open the PR in your browser with the template filled in
gh pr create --base develop --web
Reviewer (a different teammate)
gh pr list                          # find the PR number, e.g. 15
gh pr view 15 --web                 # read the diff and leave comments on GitHub
gh pr review 15 --approve -b "Checked §0 against the template guidance; reads clearly."
Author, after approval + green CI
gh pr merge 15 --squash --delete-branch
git switch develop
git pull                            # your merged change is now in develop

Commit often, push daily

You can repeat steps 4 to 9 many times on one branch: every git push updates the same pull request. Small, frequent commits are easier to review and much easier to undo.

Used an AI tool?

Add a trailer line to the commit message, and say so in the PR. Prose in the proposal must be your own writing; AI may check grammar and give feedback.

A commit with an AI trailer
git commit -m "feat(prototype): add login endpoint (#27)" -m "Assisted-by: Claude"
STEP 3

HW#4: write the Abstract and Introduction

Whole team · due Sun Oct 4, 11:59 PM · one Word file per team on Canvas

HW#4 is the short version of the proposal: the cover page, §0 Abstract and §1 Introduction. HW#4 does not require a prototype; prototype work starts in Sprint 2. You write it in proposal/proposal.md, which already has every section heading and the template's own guidance in quote blocks (> lines).

3.1 Split the writing so people are not editing the same lines

Two people editing the same paragraph on two branches causes a merge conflict. Give each person a section. A good split for a 4-person team:

IssueSection of proposal.mdBranch
Task: Fill the cover fieldsheader block (title, group, sponsor, authors, date, repo URL)feature/<n>-cover
Task: Draft §1 background§1 Introduction, first half: the field, for a reader with a CS degreefeature/<n>-intro-background
Task: Draft §1 problem & difference§1 Introduction, second half: the problem, why it matters, how you differfeature/<n>-intro-problem
Task: Draft §0 Abstract§0 Abstract, written last, after §1 is mergedfeature/<n>-abstract

3.2 File one task issue per row

Quote the labels exactly; some contain a colon and a space. The command prints the new issue's number; that is the <n> you use in the branch name.

Git Bash / Terminal
gh issue create \
  --title "Task: Draft §1 Introduction background" \
  --label task --label documentation --label "priority: high" \
  --milestone "Sprint 1" \
  --assignee @me \
  --body "## Task
Draft the background half of §1 Introduction for HW#4.

## Deliverable
proposal/proposal.md §1

## Definition of done
- [ ] Background readable by someone with a CS degree who does not know our area
- [ ] Every claim that needs a source cites one [n] in §8
- [ ] Quote-block guidance for this part deleted"

In PowerShell, replace each trailing \ with a backtick `, or put the whole command on one line.

No story points on these

Story points go only on objectives (user stories), filed in Step 5. Writing tasks carry no sp: label. On develop the check only warns that a task has no parent yet; you can link it later.

3.3 Write, one branch per task

Follow the loop from Step 2. For the background task, say its issue is #14:

Git Bash / Terminal
git switch develop && git pull
git switch -c feature/14-intro-background
code proposal/proposal.md             # write under "## 1. Introduction"; delete its > guidance lines as you go
git add proposal/proposal.md
git commit -m "docs(proposal): §1 background (#14)"
python .github/scripts/check_repo.py
git push -u origin feature/14-intro-background
gh pr create --base develop --web     # body must include:  Closes #14

3.4 What each section must contain

SectionMust includeCommon mistake
§0 AbstractBackground/motivation (1–2 paragraphs), the problem, your proposed idea, why it is non-trivial or significant, goals and outcomes (1 paragraph), and a 1–2 sentence outline of the document. At most one page.Writing it first. Write it last, from the finished §1.
§1 IntroductionBackground for a reader with a B.S. in CS who does not know your area; motivation; the problem; why solving it matters; what makes yours different from existing work.Assuming the instructor is the only reader.

3.5 Turn it in on Canvas as Word

Canvas takes one Word file per team, formatted in the course template: Times New Roman 11-pt, 1.5 line spacing, 1.0-inch margins, the template's cover page unchanged.

Easiest route: open CPSC 490 Project Proposal Template Fall 2026.docx, and paste each section's text in with Home → Paste → Keep Text Only, so the template's styles and numbering apply. Do not type the 0. / 1. numbers; Word numbers the headings itself.

Or convert with pandoc, then delete the typed numbers in Word and check the formatting:

Git Bash / PowerShell
winget install pandoc                  # once (macOS: brew install pandoc)
pandoc proposal/proposal.md -o proposal.docx --reference-doc="CPSC 490 Project Proposal Template Fall 2026.docx"

The Markdown stays the source

Keep proposal/proposal.md current after you submit. The Preview (Nov 29) and Final (Dec 20) papers grow out of it, and CI can only read the Markdown.

STEP 4

HW#5: Related Work, Problem Statements, Goals and Objectives

Whole team · due Sun Oct 11, 11:59 PM · Word on Canvas

HW#5 grows the proposal into its formal shape: Abstract and Introduction (revised from HW#4 feedback), then §1.1 Related Work, §1.2 Problem Statements and §2 Goals and Objectives. The goals and objectives are what you turn into issues in Step 5, so they are the bridge to Sprint 2.

4.1 File the tasks, then branch per section

Git Bash / Terminal · one issue per section
gh issue create --title "Task: Revise §0–§1 from HW#4 feedback" --label task --label documentation --label "priority: high" --milestone "Sprint 1" --assignee @me --body "Deliverable: proposal/proposal.md §0–§1"
gh issue create --title "Task: Write §1.1 Related Work (comparative table)" --label task --label documentation --label "priority: high" --milestone "Sprint 1" --assignee @me --body "Deliverable: proposal/proposal.md §1.1"
gh issue create --title "Task: Write §1.2 Problem Statements P1..Pn" --label task --label documentation --label "priority: high" --milestone "Sprint 1" --assignee @me --body "Deliverable: proposal/proposal.md §1.2"
gh issue create --title "Task: Write §2 Goals and Objectives" --label task --label documentation --label "priority: high" --milestone "Sprint 1" --assignee @me --body "Deliverable: proposal/proposal.md §2"

Assign each to a different person: replace @me with a teammate's GitHub username.

4.2 What each section must contain

SectionWriteCheck before you open the PR
§1.1 Related WorkA comparative analysis, not a list of summaries. Fill the table in the skeleton (existing approach · what it does · pros · cons · why ours differs), then argue in prose what you do differently and why it is worth doing.At least 3 real sources, each cited [n] and listed in §8. Every source is one you actually read. AI tools invent citations; verify each one exists.
§1.2 Problem StatementsShort, numbered P1, P2, …, a few sentences each. No background (that is §1) and no solution (that is §3). Fill the Problem → Addressed by table.Every problem maps to a goal in §2, and every goal maps back to a problem.
§2 Goals and Objectives2–3 goals (general). Under each, objectives that start with an action word and carry a measure: "Classify updates as breaking, potentially breaking or informational, with roughly 75–80% accuracy."No goal is a paragraph with no objectives under it. No objective is just a feature name ("the voting system").

4.3 Leave room for issue numbers in §2

Write §2 in this shape. After Step 5 you replace each #〈n〉 with the real issue number. The course check (gate G8) fails if an epic or story exists that §2 does not link.

proposal/proposal.md · §2 shape
- **Goal 1: Secure account management** (Epic #〈n〉)
  - Objective 1.1: Implement member registration and login with hashed

  - Objective 1.2: Demonstrate the login round-trip in a runnable

- **Goal 2: …** (Epic #〈n〉)
  - Objective 2.1: … (#〈n〉)
STEP 5

Turn goals and objectives into issues

Whole team · start as soon as §2 has a draft · locked by Sun Oct 11, the end of Sprint 1

Deadline: end of Sprint 1

By Sun Oct 11 your Goals and Objectives must be locked in: every goal in §2 filed as an epic, every objective as a user-story with assignee, milestone, priority, points and acceptance criteria, and every issue number written back into §2. Sprint 2 specifications, designs and prototype work are planned from exactly this set, and the final report is graded against it.

Your board is built from §2. Each goal becomes an epic issue, each objective a user-story. The work that delivers an objective hangs underneath it. Click through the course example to see a finished chain: #1 goal → #3 objective → #6 feature → #5 task → #7 sub-task.

Git Bash / Terminal

- [ ] #

Epics get no milestone and no points; they span several sprints.

A story needs five things the moment it enters a sprint: one assignee, a milestone, a priority, story points and acceptance criteria.

5.3 Link children to parents

Web (recommended): open the parent issue → Create sub-issue → Add existing issue → pick the child. The board then shows a parent column and a progress bar for free.

Also keep the parent's checklist current, so progress is visible in the text too. Open the epic, edit its body, and list its stories:

Git Bash / Terminal · update the epic's checklist
gh issue edit 20 --body "## Goal
Members' data is private: only authenticated users reach their own records.

## User stories (objectives)
- [ ] #21
- [ ] #22

## Success measure
A user can register, log in, and see only their own data in the prototype."

Tasks, features and bugs name their parent in their body under ## Parent (the issue templates already have that heading). Merging into main is blocked while any non-epic issue has no parent.

STEP 6

Set up the Sprint Board under Projects

Leader drives, team watches · about 15 minutes

The board is one GitHub Project. Its columns show where a card is in its life; the milestone on the issue says which sprint it belongs to; the sp: label says how big it is. Copy the live example: github.com/users/kyoungshin/projects/1.

6.1 Find the board (bootstrap usually made it)

Git Bash / Terminal
gh project list --owner OWNER          # OWNER = the account that owns your repo

If nothing is listed, create it: on GitHub go to your repo → Projects → New project → Board, name it after your repo. Then open Settings → Status on the board and make the columns exactly:

Backlog → Sprint To-Do → In Progress → In Review → Done

On the board's menu, choose Link to repository and pick your repo, so it shows under the repo's Projects tab.

6.2 Add every issue to the board

Use the project number from gh project list (say 3):

Git Bash / Terminal · one issue
gh project item-add 3 --owner OWNER --url https://github.com/OWNER/REPO/issues/21
Git Bash · all open issues at once
for n in $(gh issue list --state open --limit 200 --json number --jq '.[].number'); do
  gh project item-add 3 --owner OWNER --url "https://github.com/OWNER/REPO/issues/$n"
done

Or, on the board, click + Add item at the bottom of a column, type #, and pick the issue.

6.3 Add the three views by hand

GitHub cannot create views from the command line. At the top of the board, use + New view three times:

View nameLayoutSettingsUse it for
Sprint BoardBoardColumn field: Status. In Fields, turn on Milestone, Labels, Assignees so the sprint and points show on each card.daily work
Current SprintBoardSame as above, plus filter milestone:"Sprint 1". Change it to "Sprint 2" at the boundary.what you look at most days
Sprint PlanTableShow Milestone, Status, Labels, Assignees. Group by: Milestone.planning and the sprint review

6.4 Plan Sprint 1 on the board

  • Drag the stories you commit to from Backlog into Sprint To-Do. Each one must already have assignee, milestone Sprint 1, priority and sp:.
  • Move your card to In Progress when you create its branch, and to In Review when you open the PR.
  • Nothing goes to Done by dragging. A card is done when its PR is merged (the Closes #n line closes the issue).
  • Paste the board's URL into your team README.md (it is a README requirement).
STEP 7

Measure story points at the start and end of Sprint 1

Leader or QA owner · at planning, then again on Oct 11

You need two numbers for the Sprint 2 meeting: how many points Sprint 1 started with, and how many it finished. Nobody counts by hand; scripts/sprint_report.py reads the sp: labels and Sprint N milestones straight from your issues.

7.1 Run the report

Git Bash / macOS Terminal
GITHUB_REPOSITORY=OWNER/REPO GITHUB_TOKEN=$(gh auth token) python scripts/sprint_report.py --sprint 1
Windows PowerShell
$env:GITHUB_REPOSITORY = "OWNER/REPO"
$env:GITHUB_TOKEN = (gh auth token)
python scripts/sprint_report.py --sprint 1

It prints one row per sprint:

example output
Sprint    Window           Committed  Added mid  Completed  Open/carried  Closed late  Done %
-------------------------------------------------------------------------------------------
Sprint 1  Sep 27 – Oct 11  0          13         0          13            0            0%
ColumnMeaning
CommittedPoints on stories that were in the Sprint 1 milestone before the sprint began (Sep 27).
Added midPoints on stories put into Sprint 1 after it began.
CompletedPoints on stories closed inside the sprint window.

Sprint 1 is a special case

Sprint 1 began Sep 27, and most teams are filing their stories now, so the report counts them as Added mid, with Committed near 0. That is expected this once. For Sprint 1, your starting total = Committed + Added mid on the day you finish planning. Save that number now, because it keeps growing if you add stories later. From Sprint 2 on, plan before the sprint starts so it lands in Committed.

STEP 9

When git goes wrong

Anyone · reference

What you seeWhat it meansFix
! [rejected] … (fetch first) on pushSomeone else pushed to this branch.git pull, then git push again.
You edited files while on developYou forgot to branch.git switch -c feature/12-name. Your uncommitted edits come with you.
protected branch / push to develop refusedDirect pushes are blocked on purpose.Push a feature branch and open a PR.
CONFLICT (content)You and a teammate changed the same lines.See the commands below.
CI red: PR links an issue…The PR body is missing Closes #n, the AI disclosure or the "verified" line.Edit the PR description on GitHub; CI re-runs.
CI red: Repository harnessA course check failed (headings, links, unlinked issues).Run python .github/scripts/check_repo.py locally; it names the file and the rule.
git branch -d says not fully mergedSquash-merge made a new commit, so git cannot see your branch inside develop.If the PR shows Merged, use git branch -D feature/12-name.
Committed the wrong file, not pushed yetThe last commit needs changing.git reset --soft HEAD~1, fix, and commit again.
Resolving a merge conflict
git switch feature/12-abstract
git pull origin develop              # bring in the latest develop; git reports CONFLICT
git status                           # lists the conflicted files
code proposal/proposal.md            # find <<<<<<<  =======  >>>>>>> and keep the right text; delete the markers
git add proposal/proposal.md
git commit -m "merge develop into feature/12-abstract"
git push
Where am I? (safe to run any time)
git status                     # current branch + changed files
git branch                     # your branches; * marks the current one
